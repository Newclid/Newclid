Backend result model
====================

The backend runner returns Pydantic models defined in ``runner_models.py``. These
models are the internal source for the JSON result exposed by the job result
endpoint.

Backend run result fields
-------------------------

``NewclidRunResult`` contains:

.. list-table::
   :widths: 28 72
   :header-rows: 1

   * - Field
     - Meaning
   * - ``status``
     - Runner status: ``succeeded``, ``failed``, or ``timed_out``.
   * - ``message``
     - Human-readable result summary.
   * - ``proof_text``
     - Full proof text, or ``null`` when unavailable.
   * - ``proof_sections``
     - Structured proof sections for the proof UI, or ``null`` when unavailable.
   * - ``run_info``
     - Solver statistics, when available.
   * - ``sketch_points``
     - Final point coordinates extracted from proof data.
   * - ``stdout``
     - Captured standard output. Usually empty in the current in-process runner.
   * - ``stderr``
     - Captured diagnostic output such as truncated tracebacks.

The shared frontend/backend contract is :doc:`../../contracts/proof_result_model`.

Backend proof sections
----------------------

``NewclidProofSections`` mirrors the structured proof sections generated by
Newclid and adds one frontend-oriented field:

.. code-block:: text

   step_premise_indices: list[list[int]]

Each entry corresponds to one proof step and lists earlier proof-step indices
that were used as premises. The backend builds this from Newclid's predicate ids
so the frontend can render proof dependencies directly.

Backend sketch points
---------------------

``SketchPoint`` contains a point name and numeric coordinates:

.. code-block:: text

   name: str
   x: float
   y: float

The model validates that point names are not empty. Coordinates are converted to
plain floats before they leave the runner.

Backend result stability rule
-----------------------------

Frontend code should depend on the backend result model, not on Newclid's
internal objects. When Newclid changes its proof internals, the backend runner
should adapt those objects to the stable result fields documented here.
